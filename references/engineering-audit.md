# 工程审计与回归矩阵

用于验收被大规模改写、合并外部模块或声称修复多个 BUG 的宝典版本。

## 1. 建立基线

记录最后一个已知可用提交，并在独立分支上审计候选版本。先比较：

- `git log --stat`：识别混合提交；
- `git diff BASE..CANDIDATE --name-status`：分类新增、删除、重写；
- 公共脚本入口、参数、返回结构和 JSON schema；
- 生成物目录与运行状态文件是否被纳入版本库。

不要用 `git pull` 覆盖存在本地改动的副本；先 `git fetch`，再对比 `HEAD` 与 `origin/main`。

### 与外部发布版本对照

1. 用 `git status -sb`、`git rev-parse --short HEAD` 确定本地状态；用 `git show <ref>:SKILL.md` 核对目标提交的版本，再用同一 ref 读取矩阵和装配代码。按 JSON 键计数，区分动作、调度原语与转场；缺少同名 ID 时再查别名和等效行为。
2. 网页徽标与正文冲突时，从实时 DOM 的 `document.scripts` 找主脚本。取得公开的目标版与相邻前版资源，检查响应类型、正文和内部版本标记，再用 `difflib.unified_diff` 比较。单列相邻版差异与跨多版累计变化；拿不到历史证据时只报当前可见功能，不猜首次发布版本。
3. 区分视角（如侧面、俯拍）与相机运动（如固定、慢推），避免把新构图误报为新运镜。外部修复只提出本地回归假设：用双人→单人→双人连续镜检查最终提示词与图槽，按角色验证画外人物的表情不残留、合法画外音保留、回到双人镜后人物恢复。不要以控件隐藏或角色名出现次数代替产物检查。

## 2. 变更分类

将每项改动归入以下类别并分别验收：

| 类别 | 重点检查 |
|---|---|
| 规则/文档 | 示例命令、版本、路径和名称是否与实现一致 |
| 核心代码 | 公共函数、参数、返回结构和旧输入兼容性 |
| 门禁 | PASS/FAIL 条件、纯文戏豁免、状态推进 |
| 渲染执行器 | dry-run、点火授权、payload/schema、路径 |
| 外部模块 | 身份清洗、导入路径、输出契约、来源残留 |
| 生成项目 | 运行目录、资产、状态、渲染产物不得进根目录 |

混合提交不得以“修复 BUG”等泛化标题作为验收证据。

## 3. 测试顺序

1. 对所有 Python 文件运行 `py_compile`。
2. 运行仓库内置 `selftest.py`、`dryrun_test.py` 和外部模块自测。
3. 用合法、可解码的最小资产 fixture；零字节或伪造图片不能作为 Gate 1 测试资产。
4. 逐字执行 README/SKILL 中的 CLI 示例；记录脚本路径执行与 `python -m` 执行结果。
5. 对纯文戏、纯肉戏、文肉混合分别运行真实生成器。
6. 对 `9:16`、`16:9`、`1:1` 分别运行；每次检查生成的 aspect、分辨率、镜头结构和 JSON 帧长。
7. 逐步运行 Gate 1~6；某一 Gate 阻断时只报告该阻断，不声称全链路通过。
8. 扫描残留的上游 skill 名、作者名、版本 banner、绝对路径、运行目录和外部项目文件。

### 对白和站位的端到端核对

用导演实际采用的 Markdown 分镜，不只用程序生成的测试稿。逐镜对照“谁在场、谁入画、谁出声、道具还在谁手中”，检查场次之间是否串位。让画面只拍听者、声音来自画外，再切回双人镜。比较批量任务与离线图中 `MiniMaxH3ReferenceToVideo` 的文本输入和前三个图槽；中文方位出现在台词而不是调度栏时，不能触发换边。保留原稿，改动其副本，验证旧批次被拒绝。门禁应检查批次所绑定的执行分镜，而不是只看旁边恰好有一份同名文件。

## 4. CLI 兼容规则

文档示例就是接口契约。若文档使用 `speaker:text|speaker:text`，实现必须支持该形式，或同步修正文档并加回归测试；不要只测试自己知道的索引格式。

外部脚本的导入必须同时适配：

```bash
python scripts/module.py --help
python -m scripts.module --help
```

## 5. 报告格式

审计报告必须区分：

- 已通过的实际测试；
- 已发现并修复的缺陷；
- 被 Gate 阻断的场景；
- 尚未验证的模型、视频、音频或外部依赖；
- 不能从编译或 selftest 推出的结论。
